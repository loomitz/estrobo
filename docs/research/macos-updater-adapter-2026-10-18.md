## Integración y autoridad

`SparkleUpdateService.makeProduction(lifecycle:bundle:) -> any UpdateService` es la única factory de producto. Requiere bundle `mx.loo.estrobo`, build numérico/canal explícito, clave pública EdDSA canónica de 32 bytes, Sparkle 2.10.0 y las tres opciones de firma exigidas. Sin configuración válida devuelve un servicio indisponible sin iniciar red. El feed de producto es fijo: `https://estrobo.app/updates/macos/appcast.xml`. La falta actual de raíz/feed público es un estado de desarrollo deliberado; no se genera una clave de producción durante pruebas.

La composición de ticket 16 crea una sola `UpdateInstallationLifecycle(blockReason:restoreWindow:)`, entrega la factory al coordinador y reenvía `applicationShouldTerminate` a ese puente. Conecta `ordinaryQuitRequested` a la invalidación del consentimiento del coordinador. El puente mantiene `.idle/.preflighting/.preparing/.ready/.committing`; ninguna continuación de Sparkle escapa a la UI o al AppDelegate. La preparación consulta el cierre nativo y conserva la interacción normal devolviendo `.terminateCancel`; el compromiso final vuelve a consultar el cierre y usa `.terminateLater` hasta el callback público del instalador. El coordinador conserva su suspensión de operaciones hasta el resultado asíncrono real.

Las solicitudes internas de terminación se distinguen únicamente durante la llamada síncrona a `NSApp.terminate` desde el RunLoop principal. Un Cmd-Q o cierre externo mientras una solicitud interna está encolada invalida el intento, espera la cancelación real y sólo entonces reintenta la salida ordinaria. Un veto restaura la ventana. No fuerza cierre ni modifica datos, drafts o sesión del radio.

## Catálogo, descarga y cache

Sparkle tiene desactivados scheduler, descarga automática y profiling. Cada check hace primero un HEAD propio sin cache; un status no exitoso conserva `httpStatus` y `Retry-After` público y no inicia Sparkle. Después Sparkle valida el catálogo firmado mediante su transporte público estándar. La firma se exige antes de leer ofertas/notas, también por elemento. Los candidatos requieren build canónico, versión numérica, canal, compatibilidad, DMG completo y URL exacta de `loomitz/estrobo/releases/download/TAG/estrobo-TAG-macos-universal.dmg`, consistente con versión/canal/build. No usa API de Releases, tokens, aliases, ZIP ni deltas. Conserva un candidato compatible anterior frente a builds con requisitos posteriores.

Las notas EN/ES son extensiones autocontenidas firmadas `estrobo:releaseNotesEn/Es`, limitadas a 16KiB por idioma. La app no solicita notas remotas ni ejecuta JavaScript. La UI elige según el idioma de Estrobo, independientemente del locale del sistema.

La transferencia propia usa `URLSessionDownloadTask` con delegate real en cola serial de fondo, progreso incremental, cancelación y límite de 64MiB. El status HTTP tiene prioridad sobre el límite de bytes: 403/429 con body mayor al DMG conservan status/plazo. Sesiones efímeras sin cookies, credenciales ni cache persistente; el destino inicial es HTTPS exacto y sus redirects sólo admiten proveedores GitHub esperados. El catálogo tiene política distinta: Sparkle conserva sus redirects HTTPS estándar sin un veto previo de hosts ajenos, como acepta la decisión 15. ATS permanece sin excepciones de HTTP externo y Downloader XPC permanece desactivado.

Se conserva como máximo el último descriptor válido y una transferencia actual. Reemplazar `download.json` es atómico; una descarga fallida/cancelada preserva el paquete anterior. La limpieza elimina sólo archivos regulares propios `archive-UUID.dmg[.partial]`, sin seguir symlinks ni borrar archivos desconocidos. Longitud/SHA256 comprueban identidad local, sin pretender autenticar el archivo: la autenticidad corresponde a EdDSA de Sparkle.

Instalar exige intención explícita, validación local, gate AppKit y un nuevo catálogo firmado dentro del intento. Identidad distinta, retirada, incompatibilidad o falta de red rechazan la instalación. El archivo validado se admite a URLCache sólo después de esa intención y se entrega usando `.returnCacheDataDontLoad`; un miss falla sin buscar otro paquete. La capacidad de admisión virtual es 2GiB para un único archivo de hasta 64MiB, sin asignar esa memoria completa. La prueba midió cero refetch tanto en éxito como con cache evictada. No se promete un plazo global de retirada para caches/CDN públicos aún no desplegados.

## Pruebas y correcciones observadas

El fixture [reproducible](../../prototype/MacUpdaterAdapterCheck/README.md) comparte código de producto y usa clics/teclas `NSEvent` y consultas nativas AppKit. Cubrió discovery sin preparación, cancelación de GET Sparkle demorado y reintento, feed adulterado, identidad URL/build/canal inconsistente, Retry-After numérico/HTTP-date, canales/compatibilidad, retención de disco, cancelación de transferencia nueva preservando cache, Cmd-Q/última ventana/reinicio sin consentimiento, bytes locales adulterados, cambio y retirada frescos, veto inicial/final, cancelación preparada, carreras de quit en solicitudes encoladas, cache miss sin refetch, 403/429 con body grande, redirect externo, truncado y archivo con firma real inválida. Finalmente instaló y relanzó la versión estable real.

Los fallos descubiertos por esas acciones se corrigieron antes del resultado verde: el convenience async download no emitía progreso en este host, así que se usa el delegate de transferencia real; la cancelación se acredita al terminar el ciclo, no al devolver `cancel()`; y un `SUNoUpdateError` legítimo del bundle estable se acepta sólo en una comprobación con dominio `SUSparkleErrorDomain`, feed validado, ningún candidato seleccionado y ningún fallo previo. No transforma un candidato rechazado ni una retirada durante instalación en éxito.

Para el DMG adulterado Sparkle emite el callback de UI «start extracting» antes del resultado de su verificación. Ese nombre no demuestra extracción insegura. La evidencia acredita error real de firma/validación (4005 → 3002), ausencia de `showReady`/instalación y build anterior conservado, con `SUVerifyUpdateBeforeExtraction=true`. No se afirmó que el callback de UI no ocurra.

Además pasaron el check completo nativo/módulos, 14 escenarios de coordinador, interacción de edición y controles de ventana, y cinco tests del propietario de recursos/limpieza. Tras corregir la anotación Sendable del RunLoop, el check completo no emitió warnings. Los snapshots JSON conservan títulos/estados de controles; los PNG de bitmap salieron negros en este host y están excluidos de la evidencia visual. La apariencia, VoiceOver y contraste del producto corresponden a la aceptación de UI13/16, no a esos bitmaps.

## Límites de distribución

Ejecución ARM64, macOS27.0.1, Xcode completo, apps ad hoc **sin App Sandbox** y servidores loopback HTTP limitados a compilación de test. Esto no acredita todavía una pareja Developer ID/notarizada, Installer XPC sandboxed, Intel, runtime macOS13, permisos de autorización, falta real de espacio, DMG montado/sólo lectura, reemplazo interrumpido, conservación de datos/Keychain de producto, BLE físico ni el feed/CDN/assets anónimos públicos. Los errores públicos de ubicación/autorización/espacio se preservan como tipos para recuperación en UI; no se presentan como escenarios de distribución ya ejecutados.

La investigación ATS separada de ticket 15 obtuvo `NSURLErrorDomain -1022` tanto para HTTP externo como HTTPS302→HTTP externo con SPU2.10 y Info de producción sin excepciones; el control HTTPS llegó al rechazo de firma. Ese experimento público apoya la política, pero el fixture loopback de este reporte no es prueba de ATS externo ni de sandbox. No se publicaron releases, claves ni catálogos. Ticket 12 entrega el adaptador y prueba de mecanismo; la composición completa y aceptación de distribución continúan en 16/15.
