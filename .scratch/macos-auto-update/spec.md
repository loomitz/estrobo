# Actualizaciones asistidas de Estrobo para macOS

Status: ready-for-agent
Label: ready-for-agent
Owner: loomitz
Tracker: Local Markdown
Decision authority: preferencias confirmadas en conversación y decisiones restantes delegadas expresamente por el usuario al solicitar to-spec

## Problem Statement

Los usuarios de Estrobo para macOS deben descubrir nuevas versiones por su cuenta, descargar un DMG y reemplazar manualmente la aplicación. Esto dificulta recibir mejoras y correcciones, especialmente durante la beta. Un fotógrafo necesita mantener la aplicación actualizada sin interrumpir su trabajo, perder borradores o cerrar Estrobo durante una operación con el transmisor.

## Solution

Estrobo ofrecerá una **Actualización asistida de Estrobo**: podrá comprobar y descargar nuevas versiones en segundo plano cuando el usuario lo active, mostrará la versión disponible y permitirá instalarla mediante una confirmación explícita de «Instalar y reiniciar».

El actualizador utilizará Sparkle 2, un catálogo firmado servido desde `estrobo.app` y DMG firmados de versiones exactas en GitHub Releases. El usuario podrá desactivar los automatismos y conservar la búsqueda manual. Instalar requerirá un **Momento seguro para actualizar Estrobo**, con el transmisor desconectado y sin bloqueos de cierre existentes.

La elección de Sparkle conserva una condición obligatoria: demostrar que una descarga terminada no prepara una instalación que ocurra al cerrar sin consentimiento. La implementación comienza por esa prueba técnica, antes de integrar el flujo en el producto. Si no existe una solución mantenible con APIs públicas, se detiene esa integración y se documenta el impedimento; se mantienen los requisitos acordados.

## Implementation Decisions

1. **Alcance y propiedad.** El actualizador pertenece exclusivamente al shell macOS de Estrobo. Añadir un coordinador de actualización y un adaptador Sparkle; la ventana, Ajustes y menú de aplicación comparten una sola instancia. EstroboCore, EstroboBluetooth y EstroboPersistence conservan sus responsabilidades actuales. El actualizador no introduce HTTP en el núcleo del radio ni crea una segunda sesión Bluetooth.

2. **Primer hito obligatorio: viabilidad del consentimiento.** Crear un prototipo aislado que contraste APIs públicas de la versión fijada de Sparkle. Debe demostrar descarga terminada seguida de cierre normal, cierre de última ventana y reinicio del proceso sin instalación no autorizada; también confirmación, veto AppKit, cancelación y reintento. `SUAutomaticallyUpdate` y el camino estándar de instalación silenciosa permanecen desactivados. Un callback de relaunch o un user driver personalizado no se consideran suficientes sin evidencia. Preferir una descarga/cache separada de la preparación del instalador cuando sea necesaria, usando un camino público y soportado para instalar después de confirmar. No utilizar APIs privadas, un fork de Sparkle ni criptografía propia como atajo. Documentar la relación entre el archivo descargado y el realmente instalado; no presentar una descarga como lista si el camino no puede utilizarla de manera verificable. Si el prototipo no cumple, detener la integración y dejar diagnóstico reproducible para revisar la elección del mecanismo. No sustituir el objetivo por un simple enlace al navegador.

3. **Dependencia y compatibilidad inicial.** Fijar una versión estable concreta de Sparkle 2 después de revalidar su mantenimiento, requisitos y avisos de seguridad; la investigación realizada estudia 2.10.0. Mantener macOS 13 o posterior y distribución universal Apple Silicon/Intel. La integración sigue el sistema de compilación existente; no requiere migrar el proyecto a Xcode ni añadir Sparkle a los productos compartidos con iOS.

4. **Una frontera de integración.** El coordinador expone acciones de comprobar, descargar, cancelar descarga, aplazar y confirmar instalación, más un snapshot de presentación de sólo lectura. Se comunica con un único puerto de servicio de actualización, implementado por el adaptador real o un servicio controlado en pruebas. La UI no usa tipos internos de Sparkle ni modifica directamente su instalador. El coordinador consume el estado público y criterio de cierre existentes del controlador de sesión.

5. **Consentimiento inicial y preferencias.** Comprobación y descarga automáticas empiezan desactivadas. En el segundo inicio posterior a la configuración inicial, cuando el transmisor esté desconectado y no haya bloqueos de cierre, mostrar una invitación no modal que explique las conexiones de actualización; puede omitirse y no reaparece de forma insistente. «Activar actualizaciones automáticas» habilita comprobación y descarga en segundo plano. Ajustes ofrece controles separados de comprobación y descarga; la descarga automática requiere comprobación automática. Desactivar la comprobación detiene programación y transferencias automáticas pendientes, sin impedir la acción manual. Las preferencias se conservan entre inicios y versiones; no se reescriben con defaults en cada arranque. No presentar la opción estándar que combina descarga e instalación silenciosa.

6. **Programación y búsqueda manual.** Programar una comprobación cada 24 horas mientras la app esté ejecutándose, y comprobar al arrancar sólo si ese plazo ya venció y existe consentimiento. Una sola comprobación/descarga activa; deduplicar acciones simultáneas de ventana y menú. La búsqueda manual muestra su resultado, funciona aunque los automatismos estén desactivados y no habilita éstos implícitamente. Una descarga manual requiere una acción explícita sobre la oferta. Ante fallos, respetar los tiempos del servidor disponibles en el transporte público, usar reintentos espaciados con un mínimo de una hora para tareas automáticas y permitir reintento manual. Las respuestas HTTP propias conservan status y Retry-After; no iniciar Sparkle si el preflight devuelve un error. Si una petición posterior de Sparkle falla sin exponer esos metadatos, usar un fallback conservador de 24 horas, conservar cualquier plazo de servidor conocido y no inferir headers desde mensajes localizados ni afirmar que se conoce la respuesta oculta. Conservar el siguiente intento automático permitido entre relanzamientos, para que reiniciar no evada el backoff. Nunca informar «estás actualizado» a partir de un error.

7. **Presentación.** Añadir una sección «Actualizaciones» en Ajustes y «Buscar actualizaciones…» en el menú Estrobo. Mostrar versión instalada, canal, última comprobación exitosa, versión ofrecida, notas, progreso y acciones apropiadas. Los descubrimientos automáticos aparecen como estado/indicador no modal; no solicitan permisos de notificación del sistema. Distinguir comprobando, sin novedades, disponible, descargando, descarga completada, instalación bloqueada, instalando y error. La búsqueda/descarga de la app se distingue del modo Automático de envío al transmisor. Localizar mensajes y acciones en español e inglés; incluir soporte para VoiceOver, teclado, foco y contraste.

8. **Momento seguro para actualizar Estrobo.** Buscar y descargar puede continuar durante una sesión Bluetooth, sin bloquear el hilo de UI o la cola del transporte. Instalar exige transmisor desconectado, ausencia de conexión/escaneo/desconexión en curso y ausencia de los bloqueos existentes: sincronización, aplicación, Test pendiente, edición interactiva, envío automático pendiente, recuperación y borradores que todavía pueden resolverse mediante Apply/Discard. La UI explica qué resolver y utiliza los controles existentes; el actualizador no aplica, descarta, recupera ni desconecta por su cuenta. Un borrador derivado persistido sin camino legal para Apply/Discard conserva la excepción existente que permite cerrar, siempre que su persistencia esté acreditada; no debe atrapar la app indefinidamente.

9. **Confirmación e instalación.** «Instalar y reiniciar» confirma una única oferta identificada por build y archivo firmado. Revalidar catálogo, elegibilidad, identidad de archivo y momento seguro inmediatamente antes de entregar control al instalador. Serializar la transición en el actor de UI; durante ese breve compromiso no se admiten nuevas operaciones del radio ni otra instalación. Una cancelación, cambio de oferta, nuevo bloqueo o cierre sin la acción explícita invalida la confirmación; no se guarda como autorización permanente. Conservar el veto normal de AppKit y restauración de ventana cuando se rechaza terminar. Nunca forzar cierre ni eludir el criterio de seguridad. Un paquete descargado, una salida normal o un reinicio del Mac no autorizan instalar.

10. **Reinicio y datos.** Mantener identidad de bundle `mx.loo.estrobo`, contenedor, preferencias, presets y servicio/acceso existente a Keychain. Reutilizar la migración segura ya presente para los datos heredados de beta 4; el actualizador no crea un segundo migrador. Tras una instalación autorizada, relanzar mostrando la versión instalada y recuperar el espacio de trabajo local. No conectar automáticamente al transmisor ni enviar valores al radio por el hecho de actualizar. Persistencia y recuperación incierta no se eliminan para facilitar la instalación.

11. **Canales.** Un solo appcast: elementos sin canal son estables; elementos beta usan el canal `beta`. Una instalación beta acepta ambos; una estable sólo el predeterminado estable. El canal instalado se declara explícitamente en el bundle y no se infiere del marketing version, una preferencia antigua ni el flag latest de GitHub. Al instalar una estable desde beta, el bundle estable cambia la selección a estable. El MVP no ofrece un control para entrar voluntariamente a beta desde una instalación estable y no mantiene una preferencia beta que sobreviva a esa transición.

12. **Versionado.** `CFBundleVersion` es un entero global estrictamente creciente entre todos los builds destinados a distribución, sin reiniciar al cambiar marketing version o canal. Elegir el siguiente número por encima del máximo ya asignado, aunque no se haya publicado, y registrar su asignación; esta especificación no reserva un número. `CFBundleShortVersionString` conserva la forma numérica de tres componentes; el sufijo visible beta y el tag se representan por separado. Ejemplo ilustrativo: beta `0.1.0`, build 5 → estable `0.1.0`, build 6 → estable `0.1.1`, build 7 → beta `0.2.0`, build 8; una instalación estable en 7 no recibe la beta 8. `sparkle:version` corresponde al build real. Rechazar igualdad, downgrade, discrepancias de metadata y candidatos incompatibles. Conservar la última oferta compatible cuando el catálogo incorpore versiones con requisitos posteriores.

13. **Catálogo y archivos.** La URL objetivo del appcast es `https://estrobo.app/updates/macos/appcast.xml`; es un contrato futuro, no un endpoint operativo acreditado. Cada oferta identifica build, versión visible, canal, requisitos de sistema/arquitectura, notas, longitud, firma y URL de un DMG de una release exacta en GitHub. El DMG es el mismo archivo final para instalación manual y asistida. Conservar manifiesto y checksums de release. El MVP utiliza paquetes completos, sin ZIP alternativo ni deltas. No consultar la API REST de Releases desde la app ni depender de `latest/download`; no incluir tokens de GitHub.

14. **Autenticidad.** Usar HTTPS, firma EdDSA de archivos, firma Developer ID del código/DMG y notarización/stapling del artefacto final. Requerir catálogo firmado y verificación del archivo antes de extracción. Configurar `SURequireSignedFeed` y `SUVerifyUpdateBeforeExtraction` activados, y `SUSignedFeedFailureExpirationInterval` en 0: un fallo de firma no se convierte en una oferta válida por transcurrir tiempo. Mostrar error y reintento sin ejecutar contenido no validado. El hash es evidencia de identidad de bytes, no sustituto de una raíz de confianza. Revalidar estas opciones contra la versión fijada y demostrar su operación con el adaptador real.

15. **Red y sandbox.** Mantener App Sandbox y Bluetooth. Añadir cliente de red al shell macOS y el Installer XPC requerido por Sparkle, con las excepciones Mach acotadas a la identidad de Estrobo. No habilitar el Downloader XPC opcional de Sparkle; la app sandboxed realiza la red del actualizador. Las conexiones se destinan exclusivamente a catálogo/notas/paquetes de actualización. La URL inicial del catálogo es HTTPS y fija en estrobo.app; Sparkle gestiona sus redirecciones HTTPS mediante su transporte público estándar. Se acepta expresamente que no existe un veto previo de dominios ajenos para esas redirecciones del catálogo; no prometer una allowlist efectiva sobre esa sesión. Mantener ATS sin excepciones HTTP para servidores externos y verificar el rechazo de transporte inseguro. Las descargas que realiza Estrobo usan URLs exactas de releases y una política explícita de HTTPS y proveedores esperados; la entrega a Sparkle utiliza sólo cache. No descargar notas remotas automáticamente. El entitlement de red no constituye una allowlist: documentar y capturar el tráfico real y los datos técnicos ordinarios recibidos por los destinos. Mantener desactivados profiling, parámetros de radio/usuario y JavaScript; notas autocontenidas sin recursos externos automáticos.

16. **Privacidad y fallos de red.** Documentar que el sitio y los proveedores de archivos reciben datos técnicos normales, como IP y User-Agent; no prometer ausencia de logs del proveedor. No transmitir Código del radio, UUID, nombres de dispositivos, presets, snapshots ni identificadores de estudio. No añadir analítica, crash reporting remoto o telemetría. La pérdida de Internet sólo afecta a actualización. Para instalar desde una descarga previa se exige una comprobación válida y fresca de elegibilidad dentro del intento de instalación; si no puede hacerse, mantener la app actual y permitir reintento. Una oferta retirada o invalidada deja de estar disponible para instalar desde cache. La retirada no puede deshacer una instalación ya comprometida ni promete propagación instantánea.

17. **Empaquetado.** Copiar y enlazar Sparkle preservando symlinks y permisos; verificar ambas arquitecturas y dependencias autocontenidas. Firmar explícitamente auxiliares, framework y bundle de dentro hacia fuera con Hardened Runtime y timestamp. Adaptar los verificadores existentes mediante allowlists precisas de contenido y entitlements; conservar el rechazo de ejecutables inesperados y permisos no autorizados. No desactivar globalmente verificaciones ni usar firma profunda como sustituto de la firma de cada componente. Conservar evidencias de código, framework, permisos y artefacto final antes de distribución.

18. **Publicación y responsables.** El mantenedor `loomitz` custodia la clave EdDSA en Keychain del entorno local de publicación, con copia cifrada offline recuperable, separada de Developer ID y credenciales notariales. Las claves privadas no se publican en Git, GitHub Releases, sitio o logs. La app contiene sólo claves públicas. Conservar el modelo de candidato y promoción revisada existente: construir, firmar/notarizar/staple, finalizar DMG, firmar/verificar esos bytes, subir al draft, descargar/verificar el archivo exacto, publicar la release y finalmente promover el catálogo firmado. El catálogo debe apuntar sólo a assets accesibles anónimamente. La generación del sitio valida el catálogo aprobado y evita que un despliegue editorial posterior reintroduzca ofertas retiradas. CI puede verificar y construir sin adquirir autoridad para promover releases.

19. **Cache y retirada.** Servir el catálogo con revalidación obligatoria, sin `stale-if-error`; definir headers específicos para el catálogo, no extrapolar los del sitemap. Verificar su firma y contenido desde el dominio público tras cada promoción. Para retirar una oferta, eliminarla del catálogo aprobado y volver a firmar/publicar, manteniendo archivos y registro de retirada. No retaggear ni reemplazar assets inmutables. Un cliente exige catálogo nuevo al iniciar instalación; especificar y medir el comportamiento real de cache/redirecciones antes de prometer tiempos de retirada. El mismo compromiso se aplica a descargas ya terminadas, salvo instalación ya comprometida.

20. **Recuperación.** Preferir una corrección hacia delante con build mayor; revertir código no garantiza compatibilidad inversa de datos o Keychain. Fallos antes del reemplazo conservan la app actual; demostrar recuperación de un reemplazo interrumpido con el instalador real. La pérdida de la clave EdDSA con verificación de feed obligatoria y sin expiración requiere restaurar la copia o distribuir una nueva instalación manual firmada y verificada; no prometer recuperación automática mediante un feed no validado. Una rotación planificada requiere probar el puente de confianza antes de retirar claves anteriores y no cambia simultáneamente ambas raíces de firma. La automatización de rotación y downgrade queda fuera del MVP.

21. **Primer acceso y documentos.** Beta 4 no contiene actualizador: comunicar una instalación manual de la primera release que lo incorpora, manteniendo la verificación y guía actuales. Las siguientes actualizaciones usan el flujo asistido. Actualizar privacidad, soporte, notas y website en español/inglés para describir la red exclusivamente en las nuevas releases macOS; no atribuirla a beta 4 ni a iOS/iPadOS. Los enlaces de la app deben corresponder a la versión publicada y funcionar anónimamente.

22. **Secuencia de entrega.** Primero demostrar viabilidad del consentimiento; después integrar coordinador/servicio/UI y políticas de versiones; después adaptar empaquetado y catálogo; finalmente completar validación firmada y promoción operativa. No considerar cumplida la función sólo por mostrar una pantalla o superar tests con un servicio falso. La implementación puede avanzar sin más decisiones de producto dentro de este contrato; un resultado que invalide el mecanismo es un impedimento técnico explícito, no permiso para cambiar el comportamiento.

## Testing Decisions

- **Qué constituye una buena prueba.** Ejecutar acciones públicas de usuario y observar snapshot visible, archivos/versiones instalados, preservación de datos, solicitudes de red y aceptación/rechazo del cierre. Evitar assertions sobre orden interno de métodos, nombres privados, strings del código fuente o reproducciones del propio algoritmo. Utilizar fallos representativos con consecuencias diferentes, sin multiplicar tests que afirmen lo mismo.

- **Una frontera principal.** Probar el coordinador macOS completo mediante su puerto de servicio de actualización. El servicio controlado suministra ofertas, progreso, errores y resultados; se reutilizan el controlador de sesión, preferencias en memoria y transporte simulado existentes para generar estados reales de trabajo. Un reloj controlado forma parte del fixture de esa frontera para intervalos/reintentos. No crear puertos de prueba separados en cada vista, parser y operación del radio.

- **Consentimiento y cierre.** Cubrir descarga terminada seguida de Cmd-Q, cierre de última ventana y nuevo inicio, cancelación, aplazamiento, nueva oferta, doble click y nuevos cambios después de confirmar. Antes de confirmación, el build instalado no cambia. Después de confirmar, la instalación sólo ocurre una vez y sólo con el gate satisfecho. Conservar la reapertura de ventana ante un quit rechazado. Probar cada clase de bloqueo existente y la excepción de borrador persistido no resoluble, así como escaneo/conexión/desconexión y radio conectado ocioso.

- **Prueba del mecanismo real.** El primer prototipo utiliza la versión fijada y sus APIs públicas, con evidencia del comportamiento del instalador cuando sea necesario. Una simulación de eventos acredita política del coordinador; no acredita que Sparkle deje de instalar al salir. La prueba de viabilidad debe identificar qué se demostró realmente y bloquear la integración si no puede garantizar el consentimiento. No dar ese gate por aprobado en esta especificación.

- **Canales/versiones y elegibilidad.** Usar una tabla de ofertas firmadas que incluya builds iguales, inferiores y superiores, beta/estable, mismo marketing version, requisitos de macOS/arquitectura y oferta retirada. Comprobar candidatos y ausencia de candidatos desde la frontera pública, además de que instalar una estable cambia la selección posterior. Probar discrepancias de build, longitud/firma/URL y rechazo de aliases o payloads de un candidato diferente. Los números del ejemplo son fixtures, no reservas de release.

- **Red y preferencias.** Cubrir primera instalación sin consentimiento, activación, desactivación durante descarga, reinicio con preferencias conservadas, búsqueda manual sin opt-in, deduplicación, intervalo de 24 horas y reintentos con instrucciones del servidor. Incluir falta de red, timeout, respuesta 403/429, catálogo malformado o con firma inválida, archivo truncado/adulterado, redirect inseguro y cambio de elegibilidad antes de instalar. Un error no se convierte en «sin actualizaciones». Un fallo de firma sigue bloqueando después del intervalo de expiración que Sparkle usaría por defecto.

- **Persistencia y recuperación.** Verificar con datos de prueba conservación de apariencia/idioma, workspace, presets, borradores recuperables, transmisores guardados y acceso a Keychain después del reemplazo y relanzamiento. Reutilizar las pruebas de migración existentes para registros heredados sin leer ni copiar secretos reales del usuario. Comprobar cancelación de permisos, ubicación de sólo lectura, falta de espacio, fallo del reemplazo y recuperación a la app anterior utilizable.

- **Prior art.** Reutilizar los patrones de comportamiento de `WorkspaceChromeInteractionCheck` para AppKit y cierre rechazado, `EstroboSessionRecoveryCheck` para borradores/recuperación/persistencia, `InteractiveEditingCheck` para ajustes en curso, `SimulatedRadioTransportCheck` y los tests de EstroboCore/EstroboBluetooth para transporte controlado, y `SecurePersistenceCheck` para migración/identidad de datos. Los scripts existentes de release Developer ID, DMG y aprobación local son la base de validación de artefactos. Sus checks por inspección de fuente no son el patrón para nuevos tests de comportamiento.

- **UI accesible y localizada.** Ejecutar el recorrido desde menú y Ajustes en español/inglés, modo claro/oscuro, teclado y accesibilidad. Verificar progreso/cancelación, notas, explicación de cada bloqueo y que avisos automáticos no roban foco durante una sesión simulada. La misma instancia de coordinador sirve todas las superficies; abrirlas simultáneamente no duplica solicitudes ni instalaciones.

- **Gate de distribución real.** Antes de ofrecer la función a usuarios, actualizar entre dos builds exactos firmados/notarizados en un entorno aislado y feed de pruebas, con artefactos separados de las ofertas públicas. Verificar Intel y Apple Silicon, macOS mínimo soportado y una versión posterior, bundle/auxiliares/entitlements, Developer ID, tickets, Gatekeeper, versión resultante y datos persistidos. Incluir propietario de app que requiera autorización y DMG/translocación. Registrar commits, versión/build, toolchain, hashes, logs y resultado por caso. La ausencia de una plataforma o credencial deja ese gate pendiente; un mock no lo sustituye.

- **Gate de red/público.** Capturar tráfico del candidato con automatismos activados y desactivados, con y sin radio simulado. Comprobar destinos, cabeceras y ausencia de datos del transmisor/perfil; separar peticiones del actualizador de validaciones propias de macOS. Verificar catálogo y descargas anónimas reales, firma, cache, promoción y retirada. No extrapolar disponibilidad pública o permisos de publicación a partir del build local.

- **Regresión apropiada.** Ejecutar los checks compartidos y macOS relevantes para sesión, cierre, edición, persistencia, localización y empaquetado después de los cambios correspondientes. Mantener compilación de los módulos compartidos y checks iOS existentes cuando los cambios puedan afectarlos, sin convertir iOS en parte del actualizador. Separar fallos previos de regresiones nuevas. Las pruebas de radio usan simulación; cualquier validación física futura se declara por separado y no se infiere de instalar o relanzar.

## Out of Scope

- Actualización de iOS/iPadOS, TestFlight o App Store; cambios de funcionalidades Bluetooth, protocolo, potencia, Test o Multi.
- Instalación silenciosa, instalación al salir sin consentimiento, desconexión/reconexión automática y acciones del radio disparadas por el actualizador.
- Cuentas, backend de usuarios, analítica, anuncios, profiling o crash reporting remoto.
- Agentes persistentes, login items, actualizaciones con la app cerrada y notificaciones que requieran permisos adicionales.
- Entrar a beta desde una instalación estable, otros canales experimentales, downgrade automático, deltas y un segundo formato de paquete.
- Reemplazar assets publicados, retaggear beta 4, debilitar Gatekeeper, firmas o verificadores globales para que el flujo pase.
- Construir un actualizador completo propio o mantener un fork de Sparkle sin revisar la elección condicionada si el primer gate falla.
- Ejecutar implementación, crear/exportar claves, modificar infraestructura, publicar el feed o promover una release como consecuencia de redactar esta especificación. Esas acciones pertenecen a la entrega posterior y al contrato de publicación existente.
