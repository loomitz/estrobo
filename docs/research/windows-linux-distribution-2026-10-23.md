# Distribución y actualización de Estrobo para Windows y Ubuntu

Consulta: 23 de octubre de 2026. Baseline de paridad: `bf98e82637b562fff732ca82d7a92a66fe984d66`. Destinos aprobados: Windows 11 x64 primero; Ubuntu 24.04 LTS x64 después, con validación en ambos desde el inicio y descargas en GitHub Releases. Arquitectura elegida: Qt/C++ y proceso Swift local controlado por Qt.

Investigación documental: **no acredita un instalador, actualizador o paquete probado**. No hubo instalación, construcción ni cambios de CI. Las recomendaciones siguientes requieren decisión de Edo.

## Tres recomendaciones para discutir

1. **Windows: EXE firmado por usuario como primera candidata.** Inno Setup permite instalación sin solicitar elevación mediante `PrivilegesRequired=lowest`; encaja con un árbol local que contenga Qt, motor Swift y dependencias. La ausencia de elevación depende de que todos los componentes puedan desplegarse así: un prerrequisito instalado para todo el sistema puede requerir autorización administrativa. [Inno: privilegios](https://jrsoftware.org/ishelp/topic_setup_privilegesrequired.htm)
2. **Ubuntu: preferir un .deb para 24.04 sobre AppImage**, con actualización asistida completa y autenticación del sistema cuando se instale. Es una recomendación de formato: no existe aún un paquete validado. La versión fija de Ubuntu hace valiosas las dependencias declaradas e integración con su gestor de paquetes; AppImage añade FUSE y una política propia de integración/reemplazo. [Paquetes Ubuntu](https://ubuntu.com/project/docs/contributors/new-package/create-a-new-package/), [FUSE en AppImage](https://docs.appimage.org/user-guide/troubleshooting/fuse.html)
3. **Conservar la experiencia del actualizador de Estrobo, dejando pendiente su implementación concreta:** consulta manual o automática opt-in, notas, descarga con progreso/cancelación, posponer e instalación consentida en momento seguro. No confundir GitHub Releases con un actualizador ni seleccionar una biblioteca por tener un botón de descarga. La referencia macOS incluye esa experiencia, aunque su distribución productiva todavía tiene pendientes. [Referencia en el baseline](https://github.com/loomitz/estrobo/blob/bf98e82637b562fff732ca82d7a92a66fe984d66/docs/ACTUALIZACIONES-MACOS.md)

| **EXE por usuario, Inno Setup** | Instalación/desinstalación y firma; puede mantener el directorio de instalación al actualizar. [Firma](https://jrsoftware.org/ishelp/topic_setup_signtool.htm), [actualizaciones](https://jrsoftware.org/isfaq.php) | La app debe descargar/verificar y pasar por su cierre seguro antes de lanzar el instalador. `CloseApplications` usa Restart Manager y puede cerrar procesos; no garantiza preservar una sesión Godox ni el journal. [Cierre automático](https://jrsoftware.org/ishelp/topic_setup_closeapplications.htm) |
| **MSI** | Windows Installer admite paquetes correctamente preparados por usuario y por máquina. No requiere elegir instalación global. [Contextos MSI](https://learn.microsoft.com/en-us/windows/win32/msi/msiinstallperuser) | Más trabajo de composición, upgrades e integración del actualizador; el formato solo no consulta GitHub ni reproduce la UI de actualización. Valioso si aparecen requisitos de despliegue administrado. |
| **MSIX + App Installer** | Firma obligatoria, identidad de paquete y actualización fuera de Store. App Installer exige certificado confiable; un certificado autofirmado introduce distribución de confianza adicional. Sus actualizaciones pueden aplicarse silenciosamente, incluso después de posponer; no asumir que `ShowPrompt` equivale al consentimiento y momento seguro exigidos. [Políticas App Installer](https://learn.microsoft.com/en-us/windows/msix/app-installer/update-settings) |
| **.deb descargado de Releases** | Instalación administrada por el sistema, con dependencias declaradas y desinstalación. Un .deb en Releases no crea un repositorio APT de actualizaciones. |

## Composición Qt + Swift y dependencias reales

**Windows:** `windeployqt` prepara las bibliotecas, plugins, QML y traducciones relacionados con Qt; no recopila automáticamente todas las bibliotecas de terceros del ejecutable Swift. También hay que resolver el runtime C++ elegido y la distribución del runtime Swift compatible. La recomendación histórica del mantenedor Swift es distribuir el runtime con la aplicación; su lista exacta para el build productivo sigue sin probarse. **No se ha demostrado una instalación en una máquina sin toolchain.** [Despliegue Qt](https://doc.qt.io/qt-6.8/windows-deployment.html), [mantenedor Swift sobre distribución Windows](https://forums.swift.org/t/improving-the-distribution-of-swift-on-windows/65358)

**Ubuntu 24.04:** el archivo oficial de paquetes ofrece **Qt 6.4.2**, mientras la validación sintética usó Qt 6.8.3. Elegir .deb no resuelve esta diferencia. Habrá que decidir y probar Qt privado con sus plugins/dependencias o una base de compilación compatible con las bibliotecas del sistema, sin sustituir globalmente el Qt de Ubuntu. [Qt en Noble](https://packages.ubuntu.com/en/noble/libqt6core6t64)

Qt documenta bibliotecas X11/XCB, `libxcb-cursor0`, Fontconfig, FreeType y otros componentes; la lista final depende del build y plugins. También deben declararse BlueZ/D-Bus y los componentes Wayland que efectivamente se usen. Qt recomienda verificar dependencias y ejecutar en una máquina sin compilador/Qt. [Requisitos X11](https://doc.qt.io/qt-6.8/linux-requirements.html), [despliegue Linux](https://doc.qt.io/qt-6.8/linux-deployment.html)

Swift dinámico requiere su runtime y dependencias efectivas. El Dockerfile oficial contiene herramientas de desarrollo y bibliotecas; **no es una lista mínima de dependencias del producto**. El Static Linux SDK podría reducir dependencias del proceso, pero exige enlazado completamente estático y no admite `dlopen`; su compatibilidad con el motor/adaptadores no se ha probado. Tampoco elimina las dependencias gráficas de Qt. [Swift Ubuntu](https://github.com/swiftlang/swift-docker/blob/main/6.4/ubuntu/24.04/Dockerfile), [Static Linux SDK](https://www.swift.org/documentation/articles/static-linux-getting-started.html)

## Actualización asistida y autenticidad

Propuesta de contrato funcional, no implementación elegida:

1. Consultar Releases por canal/plataforma/arquitectura y comparar versiones. El endpoint `latest` excluye prereleases; no basta para definir un canal beta. La API expone notas, assets, tamaño y enlaces. [Releases API](https://docs.github.com/en/rest/releases/releases)
2. Descargar a staging con progreso y cancelación; Qt ofrece `downloadProgress` y `abort`, pero estas primitivas no verifican al editor ni instalan. La descarga cancelada no debe activar nada. [QNetworkReply](https://doc.qt.io/qt-6.8/qnetworkreply.html)
3. Verificar **autenticidad antes de ejecutar o elevar**: identidad editorial confiable, firma y hash del artefacto esperado; diseñar rechazo de versión/plataforma incorrecta y firma inválida. El digest SHA-256 de GitHub ayuda a comprobar integridad, pero por sí solo no es una firma del editor independiente del canal. Windows tiene WinVerifyTrust; su integración debe comprobar además la identidad esperada. [Assets API](https://docs.github.com/en/rest/releases/assets), [WinVerifyTrust](https://learn.microsoft.com/en-us/windows/win32/api/wintrust/nf-wintrust-winverifytrust)
4. En Linux, **instalar un .deb local no implica verificar la identidad de Estrobo**: APT autentica repositorios mediante sus metadatos, no firmas individuales de paquetes. Debe elegirse una verificación editorial del archivo descargado o una cadena equivalente. Igualmente, mostrar la firma embebida de AppImage no la valida. No se recomienda todavía un updater concreto. [apt-secure](https://manpages.debian.org/bookworm/apt/apt-secure.8.en.html), [firmas AppImage](https://docs.appimage.org/packaging-guide/optional/signatures.html)
5. Solicitar instalar/posponer. Para instalar: gate del motor, sin nueva entrega; conservar journal, cerrar BLE y confirmar salida de Swift y Qt antes de reemplazar archivos. Si el cierre seguro falla, posponer. El instalador debe actualizar **UI y motor compatibles como una unidad**.
6. Mostrar progreso de instalación mediante el instalador del sistema y su autenticación cuando proceda; distinguir cancelar descarga de interrumpir una instalación ya comenzada. Tras éxito, relanzar sólo con la política consentida. Probar fallos y conservación de datos: ningún formato demuestra por sí solo rollback seguro del journal.

## Bandeja y sesión gráfica: pregunta separada

Qt documenta `QSystemTrayIcon` en Windows y entornos Linux con StatusNotifierItem/XEmbed, detección de disponibilidad y limitaciones de eventos en GNOME sin extensiones. Esto acredita **icono y menú**, no un panel macOS con sliders/controles ni su posicionamiento. Ese panel requiere diseño y validación aparte. [QSystemTrayIcon](https://doc.qt.io/qt-6.8/qsystemtrayicon.html)

Qt tiene clientes Wayland y X11 mediante plugins distintos; soportar la sesión Wayland no acredita comportamiento idéntico del panel, menú o bandeja. La paridad macOS de cerrar la última ventana solicita terminar mediante el gate; no debe convertirse por omisión en “ocultar y seguir funcionando”. [Qt/Wayland](https://doc.qt.io/qt-6.8/wayland-and-qt.html)

**Decisiones que faltan para la ronda humana:** aceptar EXE por usuario y .deb como formatos iniciales; aceptar autenticación del sistema al instalar Ubuntu; precisar equivalencia y fallback del panel/bandeja y sesiones gráficas prometidas. Las versiones exactas de dependencias, composición privada de Qt y cadena de autenticidad necesitan validación técnica posterior.
